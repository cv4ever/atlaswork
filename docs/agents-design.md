# Agents design

Agreed on 2026-10-19 and built the same day (simulated replies). Decisions are numbered so later changes can cite them.
[design-index.md](design-index.md) lists every decision with the source files that cite it most.

## Before

- Atlas was one simulated agent behind an `Atlas` type. `ask(note)` saw only the attached note, and proposals changed nothing until approved.
- One conversation lived in `session.messages` with a global `attachedNoteId`. It now migrates into Atlas's thread on load.
- The Agents view showed a single Atlas profile, and the top-bar button, badge, and status bar assumed one agent.

## Decisions

### Agents

- **D1 Fidelity** (extended 2026-11-05; simulation removed 2026-11-09, D43; omp links removed 2026-11-10, D30).
  Real data model and UI.
  Every reply and routine answers through a real model: the live engine (D31) on the account's provider, or on the dev server the ChatGPT plan bridge.
  With nothing connected, agents say how to connect one and routines wait.
- **D2 What an agent is** (extended 2026-11-05, 2026-11-09, 2026-11-10 and 2026-11-11).
  Name, portrait, role, warmth/detail, house rules, tools, routines, write power and, optionally, a model of their own (D44).
  Warmth and detail an agent leaves unset follow Settings → Every agent, which also adds house rules every agent reads (D46).
  Every agent answers through the provider chosen in Settings → AI model; no agent has its own connection.
  Workspace tools start on; outside tools (email, calendar, web) start off, and when on the model may hand over a link you open yourself (D43); Every agent can change what a new agent starts with.
  The same tools decide what the function may read and propose (D31).
  Workbench's proactive/propose switches govern replies and routines.
  The Personality preview is a fixed line in the agent's tone, labelled as such, not a reply.
- **D3 Scope comes from assignment** (Agent's Workspace clarified 2026-11-11).
  Supplied context comes from assigned domains/projects, with everything for Atlas and explicit attached notes allowed outside assignments.
  `scopeOf` stays assignment-only; the Agent's Workspace (`src/agentWorkspace.ts`) selects live records, Page text, command choices and change Homes together.
  Archived Resources, Projects and parent Domains stay out, even when a Resource is attached; put-away Blocks stay out of Page text.
  A live attachment extends its change Home while it remains attached, not access to neighboring Resources, tasks or Page text.
  Read notes may be off while an explicitly attached note is read; task reads and change permissions remain separate.
  The export excludes completed tasks and never sends binary file bodies.
- **D4 Atlas** (extended 2026-11-06).
  Configurable: name, portrait, instructions, write power.
  Fixed: scope is everything, he can always use every tool (his switches show on and locked, so a workspace with only Atlas can do everything, arranging pages included), and he cannot be deleted or archived.
  Connections are the exception (D83): he starts with all of Google Calendar, also while you're away, and you can narrow or turn it off in Settings → Connections like anyone's.
  He answers wherever nothing else is assigned and can join any crew.

### Assignment and crews

- **D5 Cardinality** (revised the same day).
  A domain has 0 or 1 agent.
  A project has an optional assigned agent and an optional team.
  A **team** is a saved, reusable group whose first member leads; it can work on many projects and has its own room.
  The original "crew only, no Team object" answer was reversed when teams were asked for directly.
- **D6 Nearest owner.** A project's crew is its assigned agent, then its team (lead first), then the domain's agent, who joins every crew in that domain. Chat opens to the project crew, else the domain agent, else Atlas.
- **D7 Rooms.**
  A Project gets a Room when its crew has 2 or more members.
  A crew of one uses that agent's own Thread.
  Teams have their own Room, and you can start a Room with any agents you pick (`chat:` Threads, titled, deletable).
  Implicit Project and Team Rooms need no saved Thread until used.
  Started Rooms appear even before their first message.
  Existing Room history survives membership changes.
- **D8 Who replies in a room** (extended 2026-11-04).
  `@name` addresses specific agents.
  An unaddressed message goes to the first crew member.
  The composer's "To" row (first, Everyone, or one member) stays picked for that Room and adds the matching `@names` when you send, unless the message already names them, so Everyone means each member answers in order.

### Autonomy

- **D9 Owners act** (clarified 2026-11-05 and 2026-11-09; one Proposal module 2026-11-11).
  Agents act only through Workbench proposals, which follow the write mode: proposing first, or applying with Undo; the model never edits records.
  The Proposal module (`src/proposals.ts`) decides what lands from every reply and routine run and answers Apply, Reject and Undo, so chat and routines share one write-mode rule and one wording ("Undo if it isn't right." or "Nothing changes until you approve.").
  Dialogs still patch only changed fields, preserving unrelated records; deleted records cannot be recreated by stale edits.
  Reply completion and Apply recheck the originating agent's current permissions, assignments, live targets and attachment through the Agent's Workspace.
  A lost permission or target refuses the whole draft with a reason, before any proactive changes or proposal history commit; titles are never resolved onto replacement records.
  Undo retains its existing drift protection and does not require the agent still to have access.
- **D10 Routines** (revised 2026-10-22; see D20–D25).
  Each routine runs once its time has passed, the next time the workspace opens or comes back into view, or from "Run N due" and a routine's own Run now on the Routines page.
  It posts only when it acted or has something to say.
  A check-in needs Read notes and Add tasks; a report and a review need See tasks.
  Without them it waits, marked "Needs a tool".
  Enabling a missing tool leaves it waiting for those same run triggers; saving permissions does not itself run agent actions.
- **D11 Activity and undo** (extended 2026-11-05). Live replies and routines post Undo cards. Drift protection refuses undo once a touched record changed.
- **D12 Simulation** (superseded 2026-11-09 by D43). The local rule-based engine (note bullets to tasks, review rules, canned outside-tool replies) is gone; older chats keep the note-bullet proposals it made, and Apply still refuses one whose source note changed.

### UI

- **D13 Chat.**
  The right panel stays.
  A rail of faces down the panel's right edge shows Atlas, a rule, then this context's agents and Rooms, with All chats and Start a room at its foot (2026-11-17, Carlos picked the crew rail from three prototypes, `dev/chat-prototypes/`, and then moved it from the left edge to the right; the strip above the name card showed the open chat's face twice).
  A face carries an amber count of what waits on you there (proposals and questions), else a dot for unread news; the open one wears a ring in its colour.
  The rail's surface is a hand-drawn vine by default (a sage stem with leaves running down it, the faces sitting on it like buds; Carlos picked it on 2026-11-17 over deep-green ink with contour lines, a speckled seed tray and a tint of the open chat's colour, after rejecting a drawer, name tags and side tabs: he wanted the same 56px rail and faces, only a different surface); a wave of dots shows on a face while that agent replies.
  The surface is a choice the person makes (Settings → Canvas → Chat rail, `Session.railStyle`, `data-rail` on the root): Vine, Ink, Seed tray, Chat colour or Plain; each theme sets its own too (Garden and Tide vine, Linen and Frost plain, Terracotta, Meadow and Espresso tray, Dusk chat colour, Midnight ink; 2026-11-23, `src/dialogs/themes.ts`), hovering a choice previews it, and the Settings miniature ends in a small chat panel with a real rail, so the choice shows there even with the chat closed.
  Your own bubbles sit at the right edge at their own width, an agent's words run on the page, and line breaks stay; agents may split a reply that covers separate things into short paragraphs (2026-11-17), and since D64 (2026-11-18) a reply may use Markdown (ground rule `format`).
  The cards live in `src/ChatCards.tsx`, the faces in `src/AvatarStack.tsx`.
  A card an agent hands you (tasks, changes, an agent, a question) heads each section with its icon and a count in words, and shows an attention dot while it waits; Apply is the filled button and Reject and Decline are outlined in the error colour; once decided it folds to one line (accent with Undo when done, quiet and dashed when rejected, declined or undone).
  "Try asking" starters show only while nothing you wrote is on screen and the box is empty, never mid-conversation.
  There is one Thread per agent, per Project Room, per Team, and per Room you start.
  A one-to-one chat never repeats who is talking: its agent's replies carry no name or face, and a check-in, answer or follow-up gets one quiet label line ("Check-in · 16:15").
  A Room, or another agent answering in someone's chat (D50), names each voice with its face in the margin; back-to-back messages from one voice on one day drop the repeated name, and a day heading opens each day.
  Each message's time (and for yours, where you wrote it) and a Copy button sit in the gap under it, shown on hover or keyboard focus; Copy ticks for 1.5 s once copied (2026-11-17); your own bubbles highlight a selection in the accent, since their fill is the page's selection tint.
  The Room module supplies identities, membership, picker choices, current context and previews.
  The UI keeps grouping labels, colours and formatting.
- **D14 Top bar.**
  The Atlas button becomes a chat button: it shows the avatar it will open to, and its badge counts unread agent messages across all retained Threads, once per Thread.
  It floats as a bubble over the page's bottom-right corner rather than sitting in the header (2026-11-12, after Notion's AI bubble): the face alone, the name sliding out to its left on hover or focus, gone while chat is open or is the page, and while a resource's side preview is open (it has its own Ask button); phones keep the Chat tab instead.
  An agent message that lands while the app is open (2026-11-13: what was already unread at opening stays with the badge, so nothing covers the page on load) peeks out above the bubble as a speech bubble with the speaker's name and two lines of the message (their face too when the bubble doesn't already show it), plus a Review pill when it carries a pending proposal: it stays while the pointer or focus is on it, folds after 8 seconds or on ×, and opens its own conversation in the panel. Only messages newer than the last one peeked rise (this device keeps its time in `atlaswork.peeked-at`), so a reload or reading one never brings up older ones; an agent speaking in a brief on the page doesn't peek.
  While any agent replies, typing dots sit on the bubble's lower left (its tooltip names who), so a reply on its way shows with the panel shut; it peeks when it lands.
  Ctrl/Cmd+J shows or hides the chat (as in Notion), except on the Chats page; the tooltip names it. Pages end with 72px of room on desktop while the bubble is there, so it never covers their last line.
  Ask about this: selecting words in a note offers an "Ask <agent>" pill under the selection. It attaches the note to the chat the bubble opens, adds the words to the message box as a quote (after anything already typed) and puts the caret after them; nothing is sent. The note's own button names the same agent ("Ask Vital about this").
  Shrinking a Project crew or archiving its home does not remove its unread history from the total merely because the Room is no longer a live picker choice.
- **D15 Management.**
  The Agents view is the roster: Atlas, the agents, and the teams, plus Start a room.
  A project's agent and team are picked on the project page or in its dialog, the domain agent in domain settings.
  The agent dialog is a name badge (face, name, role, and a live sample reply) beside five tabs: Profile (where they look, personality, house rules), Permissions (proactive or asks first, tools), Tasks (open tasks where they look, ticked off in place), Schedule (their routines, plus the place routines they run, read-only) and Briefing (what the model is told, D46).
  The tabs carry their words, not counts (2026-11-27, Carlos: with counts the five tabs needed about 560px of the pane's 530, so Briefing was cut off on every screen); each panel states its own count, and the tab's accessible name keeps it.
  When the pane is narrower than the five words (471px: tablets and phones) the unselected tabs show only their icon, with the label as tooltip and accessible name, and the open tab's words shorten before the row would run past the dialog.
  Profile sets places too (domains, projects, teams) and saves them with the agent in one changeset; taking a place over replaces its previous agent, and a team can't be left empty.
  A new agent opens ready to save: an unused name and face, the crew's usual write mode, a daily morning check-in, and the first domain nobody looks after (or the project you created them from).
- **D16 Portraits** (extended 2026-11-12, crew styles 2026-11-26).
  The 54 selectable avatars include the Homebase cast (Hearth, Vital, Kin, Ledger, Compass, Spark, Muse, Scout, Quill, Forge), 14 earlier generated portraits, 24 additional character portraits and six neutral silhouettes (pine, clay, navy, plum, ochre and teal).
  The new set uses Muse, Forge and Vital as style references: warm gouache, fine dark outlines, paper texture and muted backgrounds, cropped to individual 464px WebP squares.
  `public/agents/` holds the images and `portraits` in `src/look.ts` is the shared catalogue for new agents, the dialog's All faces drawer and community configurations.
  The existing free-face arrows and taken-face indicators apply to the expanded catalogue without changing saved agents.
  These are bundled choices, not runtime generation.
  Crew styles (2026-11-26, Carlos chose one style for the whole crew over shelves per style in the drawer and per-agent exceptions): Settings → Appearance → Crew style redraws every portrait and Atlas in one of nine packs, Storybook (the original), Manga, Heroes, Villains (the heroes' dark twins with corrupted emblems), Pixel, Animals, Ink, Clay and Fantasy.
  An agent still saves the face's name, so a style changes no saved agent, community crew or free face; the six silhouettes stay as they are, and a face you wear as your picture follows the style.
  It is this device's choice (`Session.crewStyle`), tried on by hovering or focusing a card (`crewStylePreview` in `src/crewStyle.ts`); components draw faces through `usePortraitSrc`, so a new style redraws them all at once.
  Each pack is 49 generated 256px WebP squares in `public/agents/<style>/`, cut from 3×2 sheets that took the Storybook faces as the people and the pack's first sheet as the style (prompts in `dev/avatar-packs-prototypes/prompts.json`); they stay out of the install's precache and are cached once shown.
- **D19 Logbook** (revised 2026-11-04, see D27 and D28; renamed from History and moved to its own tab 2026-11-21).
  The Logbook lists conversations, not messages: every conversation across every chat newest first, each with its title, chat, what came of it and the place you wrote from.
  It is the Chats page's fixed tab (`view=logbook`), never a rail under a chat's tab (Carlos, 2026-11-21: a list of every agent's conversations beside the Atlas tab read as Atlas's own, so whatever sits under a selected tab belongs to that tab).
  What came of it (`outcomeOf` in `chatsPage/logbook.ts`) is read from the conversation's cards, never a model: suggestions waiting ("1 change to review"), a question to pass on, what was applied ("Added 2 tasks, made 1 change"), turned down or undone, or nothing for talk.
  An agent request (2026-11-17, `Sitting.request`) is titled by the goal without "I'd like an agent for this:" and says the draft's name and where it stands (No draft yet, Not answered, Agent draft to review, Agent saved, Draft rejected, Replaced by a newer draft).
  Whatever waits on you leads in its own "Waiting on you" group, the rest group by age.
  Filters beside the list (a row of chips on narrow pages): Show (Everything, Waiting on you, Decided, each with its count) and With (everyone, or one chat).
  Search matches chat names and message text, highlights the title and chat, and says how many messages matched without reprinting them.
  A row opens its chat as a tab, live at its first match or its start (rendering back to it if it is older than the latest 150).
  Search includes retained Project and Team Room identities, not just current picker choices.
  A saved Room with no active members opens its own read-only history instead of redirecting to Atlas.
  Deleted Threads are absent from discovery and history; a stale selection falls back to the nearest owner.
- **D26 Sidebar roster** (2026-11-04, extended the same day).
  The sidebar has two saved tabs, Projects and Agents (`Session.sidebarMode`, whose first value is still `workspace`).
  Agents lists Atlas pinned first, then the selected domain's agents under its name, then everyone else in a section that folds (revised 2026-11-19: sections replaced the All / Here filter, whose boxed toolbar cost a row on every visit); agents you've never talked to fold behind "N more" in each section, and "Show fewer" folds them back. Each section is a labelled group (`role="group"`).
  A row opens the agent's own Thread as a tab on the Chats page (D27).
  Presence comes from `presenceOf` in `agents.ts`, in priority order: working (replying in any Thread), approvals (pending proposals it posted anywhere), a question (its own Thread ends on its message ending in "?"), stuck (a failed reply, or one of its own unpaused routines needs a tool it lacks), else idle.
  `Session.roster` saves the view: whether Everyone else is open, sort by needs you first, latest message or name, detailed or compact rows, and which details show.
  The Agents page opens from "Agents" (tooltip "Agents and teams") at the foot of the Agents tab, beside Routines on one row, always in view (2026-11-20: in the popover, behind a hover-only button, Carlos couldn't find it; 2026-11-22: the pair shares a row, so the label shortened).
  Teams and Rooms stay in the strip and on Chats.
- **D27 Chats page** (2026-11-04, reworked the same day after the Homebase chat experiment).
  Two places for one Thread, with one rule: the side panel is chat beside your work, the Chats page is chat as the work.
  There is one page, `view=chats`; the earlier separate conversation page and the old Chats list/read-back were merged into it.
  It fills the content area: open chats as tabs over the live conversation, and a rail beside it.
  The tabs use the domain workspace's tab bar (`.workspace-topbar`, `.tabs`, `.tab`), so they look and behave alike: the active tab takes the accent, arrow keys move between them, and pin and close sit on the tab.
  Tabs (`Session.chatTabs`) are pinned chats first (no close button), then up to 8 others in the order opened; the one on screen always shows, deleted chats drop out, and closing the current tab opens its neighbour or leaves the page.
  The bar leads with one fixed tab, Logbook (D19), whose page takes the chat's place (the Agents tab before it left on 2026-11-22: the sidebar's Agents and Routines row already opens the Agents page, so Carlos found it redundant).
  A + right after the last tab opens a chat, like a browser's new tab: Open a chat searches every conversation, those waiting on you first, with Start a room at its foot (2026-11-26, Carlos: + by the tabs used to start a room, while opening a chat hid behind a speech-bubble icon).
  The bar ends with the page's own controls, Move to side panel and Close, far from the tabs' own × (2026-11-26: they sat in the chat's header, so a × that closed the page sat 40px under the tabs' ×); a control sits with what it acts on, the page in the tab bar, one chat in its header.
  The header's About button (`Session.chatRail`) opens the About rail: what needs you (proposals in this chat, with a jump to the first), the agent's role, places, write mode, tools and routines, each with a Change link into the matching agent-dialog tab, then Start a room, This chat in the Logbook and Configure.
  A Room lists its members instead, each opening their own chat, plus New room with these agents and, for started Rooms, Delete room.
  On narrow pages the About rail floats over the chat.
  The conversation reads at a capped line width, has a find bar (search button or Ctrl/Cmd F while focus is in it; Enter and Shift Enter step through matches), the composer's context meter (D28) and the "To" row (D8).
  The roster (D26) and the panel's expand button open a chat here as a tab; the expand also closes the panel.
  Everything else (top-bar button, rail, Today's link, attaching a note) keeps the side panel, and the panel's Logbook link and "earlier messages" open the Logbook at this chat.
  On the page, "Move to side panel" returns to the page you came from with the same Thread open beside it, and Close returns there without it, leaving the panel as it was.
  The page shows its picked Thread wherever you are, unlike the panel's per-place pick (D6), and tabs and rail survive reload; the page it returns to does not, so after a reload both go to Today.
  Phones keep the full-screen chat and have no expand button; there the rail becomes a row of faces across the top and the name one short line, the starters scroll sideways, and the row of faces and the starters step aside while the keyboard is up (2026-11-17, DESIGN.md, Layout).
  Draft, read state and unread counts are the same Thread's, wherever it shows.
- **D28 Conversations and context** (extended 2026-11-05; measured 2026-11-09, D43; renamed and clearing 2026-11-17).
  A Thread (a chat) contains conversations, starting on each local day or New conversation; the Logbook keeps earlier ones.
  The app says conversation, never session (Carlos, 2026-11-17: "session" read as technical, and the code's Session is the device's layout); code keeps `sessionStarts` and `Sitting`.
  New conversation clears the chat on screen (Carlos, 2026-11-17, after New left every message in view): what came before folds away behind a "Previous: title · when" line at the top, cards still waiting on you stay (and stay once you act on them, so Undo is at hand), and finding or a Logbook jump shows it all.
  The Previous line reads that conversation on its own, as the header's switcher (D29) reads any earlier one (2026-11-26, Carlos: "Earlier conversations" unfolded every one at once, with no way to reach one older conversation): the transcript shows only it (`transcriptWindow`'s `reading`), and a reading bar takes the message box's place, since agents start each conversation fresh, with arrows to the conversation before or after and Back to now; finding still searches the whole chat.
  A new day starts a fresh conversation for the agents but clears nothing, so New stays available until the chat is clear.
  Titles come from the first user message, else a routine or first message, with visible seams and fresh starters.
  The context meter in the composer shows measured numbers only: each live reply stores the tokens its provider reported (`ChatMessage.usage`: read, written, and its largest single call), and the meter shows the fullest member's latest window against a typical 128k ("12% context"); it opens to every member's window, this conversation's tokens, and counts replies without numbers (older ones).
  Until a reply is measured it reads "Context" and its panel says none is measured yet; the panel also names the model that answers, with Manage usage for an engine with its own plan (the ChatGPT bridge) or a link to Settings → AI model, and the crew's write mode.
  Each real responder persists its own native session reference in the Thread; reload resumes it, while New conversation/day/relink resets it.
  New conversation waits for an in-flight turn, a routine's included, and does not erase native long-term memory; on a chat that is already clear it changes nothing.
  Your message records the agents it asked (`ChatMessage.awaiting`), and each reply takes its agent off in the same write, so an agent that failed, or that a reload cut off, shows under the message as "Atlas didn't answer" (in a room, only the ones that didn't), after a reload too (2026-11-17, Carlos: a second ask after a failure stacked two requests in one conversation).
  On your latest message, while it is in the current conversation, Retry asks just those agents again (`Conversations.retry`): the message is not sent twice and their replies follow it. After a New conversation or a new day the note stays without Retry, since the reply would land in the wrong conversation.
  The note also says why, in the engine's words (`ChatMessage.failure`, gone once everyone it asked has answered), with the step that would help: Manage usage for a usage limit, Connect your own model where only one would lift the refusal; the message box then doesn't repeat it.
  With no model connected (`EngineInfo.offline`) nothing can answer, so the box says so with Connect a model, and Send, the starters and Retry wait, instead of failing each message.
  The live engine (D31) keeps no session: every request carries the current conversation's last 12 messages (`AgentRequest.history`), so New conversation and a new day start it fresh too.
  What lasts across conversations is what agents remember (D49), which every request carries.
- **D29 Conversation header** (2026-11-04; reworked 2026-11-17 with the crew rail, D13).
  The rail shows the face, so the header is the name: large Fraunces with a hand-drawn underline in the chat's colour.
  On the Chats page the tab already names the chat, so the header drops the name (2026-11-22, Carlos: two rows of chrome both said "Atlas"): one row at the conversation's width with the topic, the status and the actions; messages fade out under it as they scroll.
  Under it, the conversation's title (the first thing you asked in it, as the Logbook names it, "New conversation" in italics while the next message starts one) with a chevron, then its message count; the title is the conversation switcher (`chat/ConversationSwitcher.tsx`, 2026-11-26): this chat's conversations only, what waits on you first and then by age, each with what came of it (`outcomeOf`, as the Logbook says it) and when, the current one marked Now, New conversation at the top, a search that matches what was said, and the Logbook at its foot for every chat's.
  Under that, a status only when something needs you or is happening ("1 to review", "Replying…", a failure); the role and when they last wrote moved into the title line while a conversation is fresh ("Health coach · last wrote yesterday 19:35": the time today, "yesterday" and the time, else the date), and the rooms say "2 here · Hearth answers first".
  Waiting on you reads in ink after an attention dot, and a tap brings the first card that waits into view.
  Its actions are New conversation, Open as a page and Close in the side panel; on the Chats page Find, New conversation (worded "New") and About, the page's own controls sitting at the tab bar's end (D27).
  New conversation shows only while there is a conversation to end, never greyed out (2026-11-26, Carlos: greyed whenever the chat was clear, it looked broken); its tooltip says where you are ("Conversation 2 today, 7 messages since 2:42 PM"), and it fills in the accent with its reason when a fresh start helps (a window at 60% or more, or 3 hours since the last message).
  The context row under the header is gone (it took 46px and repeated the model's name from the header): the note they read sits in the message box as a filled chip only once attached, and until then the paperclip offers a note with a dot, its menu leading with it (never as an attached chip) before Find a note: the note you're on beside your work, else the note you last changed (`Visible.lastNote` counts only notes, never links, files or images, which left the offer empty before 2026-11-17); the model, context and write mode live behind the composer's context meter (D28).
  The offer was a "+ Attach “title”" line above what you type until 2026-11-26, when Carlos called it redundant with the paperclip and a row lost in every chat.
  The composer's tools keep their size in a narrow panel; only the dictation status gives way, cut short with its words in the tooltip.
  Overlapping faces in every avatar stack are cut out with a transparent mask gap instead of a ring in the panel colour, which showed as a white halo on tinted surfaces.

- **D30 Dev-only omp chat** (2026-11-04; removed 2026-11-10, Carlos: agents "should now use whatever is configured").
  The dev server once routed chosen agents to Carlos's real omp agents (`dev/omp/`).
  It's gone: Atlas, Forge and every other agent answer through the configured model like everyone else, with proposals, Undo and routines.
  What it left in product code went with it: `EngineInfo.caveat`, the engine-owned per-agent `Settings`, `EngineSession` on requests and replies, `Thread.engineSessions` and the AI model note about agents answering elsewhere.
  Boot strips the legacy fields (`ompAgent`, `ompThinking`, `ompSessions`, `engineSessions`) from stored records.
  The neutral seam stays: `AgentEngine.about()` returns one `EngineInfo` for every agent (`badge`, optional `offline`, `maxRequest` and `manage`; it took the agent until 2026-11-10, when nothing varied by agent any more), alongside the shared `models` state (D44), optional `localModel` (the dev ChatGPT bridge) and `subscribe`.
  An engine that keeps its own memory would bring its session handle back with it (launch plan D14).
- **D31 Live engine** (2026-11-05, accounts 2026-11-06, commands 2026-11-06, profile 2026-11-06, everywhere 2026-11-09; launch steps 4 and 5 in `docs/mvp-launch-plan.md`).
  `createLiveEngine` (`src/live.ts`) answers chat and routines through the `agent` Edge Function for a signed-in account (launch plan D15), on our model or the account's own (D16); signed out with nothing connected, `offlineEngine` answers "No AI model is connected" (D43).
  The function refuses accounts without Pro, a running trial or an own model.
  Its badge is "Live".
  Each request carries the Agent's Workspace (D3's text export), its places, the lookups its permissions allow (Read notes → `read_notes`; See tasks → `list_tasks`), the commands they allow (D33, D43) and the current session's last 12 messages (D28), with other agents' turns named.
  `createAgentEngine` selects that Agent's Workspace once per reply and builds the request from it (`snapshotOf` in `src/agentRequest.ts`); adapters only carry it to a model and bring back text, an unchecked draft and usage (2026-11-11).
  When the person filled in their profile, the request also carries `person` (their name, at most 60 characters, and their line about themselves, at most 240); the system prompt tells the agent their name and that line, and an empty profile sends nothing.
  The function returns text, at most one draft and the tokens the reply used; the engine binds the draft to identities in the same selection the request came from (`draftsOf`), then Room checks current access before admitting its Proposal or links (D43).

- **D33 Command registry** (2026-11-06, lookups, empty choices and object items 2026-11-08; `reschedule_tasks` 2026-11-08; idea taken from Herdr's single command list).
  `src/commands.ts` is the one place that defines what a live agent may change.

  **Messages one at a time** (built 2026-11-23, Carlos chose records over a server-side merge or a version check).

### Routines

Agreed and built 2026-10-21.

- **D20 What a routine is.**
  A kind (check-in, status report, review, weekly improvement, D68), a time, and a repeat: weekly on chosen days (every day and weekdays are presets) every 1–4 weeks, or monthly on a date (short months use their last day) or an nth or last weekday.
  Times are picked as Morning 08:00, Midday 12:30, Evening 18:00, or an exact time.
  Routines are separate from tasks: a task is yours to finish, a routine is something an agent does.
  The `Repeat` type is shared so recurring tasks can reuse it.
- **D21 Who owns one.**
  Agents keep their own routines, covering where they look.
  Domains and projects add their own, covering the domain's loose items plus its live projects, or the one project.
  A place routine runs under the place's nearest owner at run time (D6, then Atlas) and posts where chat opens there.
  Place routines only add; they never override an agent's.
  Archived agents, domains, and projects keep theirs and resume on restore.
- **D22 When it runs** (clarified 2026-10-22).
  Due-at with catch-up: a missed stretch runs once, for the latest due time.
  Routines set up after that time skip it.
  Only an eligible run advances `WorkspaceData.routineRuns`; a quiet success counts, a missing-tool attempt does not.
  A posted message carries `routine.due` as a second guard.
  Run now satisfies any already-due occurrence; running before the next due time does not cancel that future occurrence.
  Manual runs at the same instant do not repeat, even when quiet.
  Runs stay in the workspace, not the device Session.
- **D23 Review** (asked of the model since 2026-11-09, D43).
  Ticks off open tasks the notes in scope show as done, gives overdue tasks new days (today or soon), files tasks sitting straight in a domain into the domain's project they're plainly a step of (D61; never across domains, only into existing projects, with `move` changes), and archives live projects where no resource or task was touched in 30, 60 (default), or 90 days and nothing is open from today on: the browser computes which projects qualify and offers only those (`quietProjects` in `commands/request.ts`).
  Tasks carry `updatedAt` for this; a project with no timestamps at all isn't judged.
  It follows write mode (D9).
  A proactive review (a routine run) makes at most 5 changes itself; the rest post as a second, pending card.
  A review the person asked for in chat has no cap.
  Undo restores every change unless one was edited since.
- **D24 Routines page** (clarified 2026-10-28; preview 2026-11-09).
  A sidebar destination.
  Since D68 and D70: one sentence of what's on, due and next, the next seven days as faces on stems, filters by agent and state, then every routine as one row that opens its sheet beside the list (D70); New routine adds one for any agent, domain or project.
  The same list appears in the agent dialog's Schedule tab and in the domain and project dialogs, where a routine opens its detail in place of the list (D70).
  The editor asks what, how often and when, then shows the next four runs and what its runner is asked to do (a run asks the model, D43, so there's no guess at the answer).
  "Run N due" and Run now wait for the answers and say how many ran, how many had something to say, and why one failed.
  Dialog previews use the same Workspace edit as Save, including Domain rename propagation into Projects, Resources and Tasks.
  Domain and Agent lists retain current routines until that list is explicitly edited.
  Invalid or deleted owners show a refusal, not a hypothetical runnable owner.
- **D25 Readiness ownership** (implemented 2026-10-22).
  The Routine module's `readinessOf` (its `Readiness` type) is the shared interface for the page, editor, week line, draft counts and Room execution.
  It owns runner, live owner, tools, pause and stored/posted run receipts for scheduled/manual eligibility.
  Workbench's `admitRoutine` owns current eligibility plus the durable claim and checks live eligibility again after the write; Room keeps posting and action/history commits.
  IndexedDB uses one read/write transaction; the account's `claim_routine` locks its receipt row and applies the existing quota.

### Storage and lifecycle

- **D17 Storage.** Agents, assignments, and Threads are Workspace records: exported, backed up, and kept in step with renames, archiving, and deletion. Deleting a Project also deletes its Room history and unread contribution.
- **D18 Removal.**
  Archive asks first, removes the agent from domains and crews (the nearest-owner chain fills the gap), remembers those places, and keeps its thread read-only.
  Restoring puts it back wherever nobody has taken its place since (as a team member, not lead).
  Delete forever also removes the thread.
  Its past edits stay.

## Assumptions

- Agent names are unique (case-insensitive), so `@mentions` are unambiguous.
- A thread is read when opened in the panel. "All chats" is a popover grouped by domain with unread counts.
- On mobile, the chat view lays the rail of faces in a row across the top.
- Routines skip archived domains and projects.
- Within one run, agents' routines go first, then domains', then projects'. If two touch the same item, both actions are logged, and D11 makes only the later one undoable.
- The existing `session.messages` conversation becomes Atlas's thread.

## Implementation

- `src/conversations.ts` owns Room discovery and lifecycle behind one interface shared by the side panel and Chats.
  `discover(domain, projectId?, pickedId?)` derives `ThreadSummary` records, picker choices, the current Thread and strip, retained history sittings, read-only state and total unread from the current Workspace.
  Discovery does not persist implicit Threads.
  Sittings keep the existing thread-change cache.
  It reuses the Crew rules in `agents.ts` and the existing `AgentEngine` seam, without a new module or adapter.
- Proposal task edits and the matching thread message or status form one changeset. A failed save cannot persist the action without its history.
  `src/proposals.ts` returns both as one Change for the Room to commit, and never commits itself.
- In-flight replies are scoped to their thread and initiating message. Deleting the thread or removing its responder prevents a late reply from restoring it.
- `src/routines.ts` derives readiness from both run records and posted messages. The page and execution therefore agree when a message survives without its run record; pending proposals do not repeat after reload or on another device.
- `src/workbench.ts` owns current Workspace and Session records, migration, save status, and retry. Its IndexedDB adapters and the transactional in-memory adapter in `workbench.test.ts` cross the same seam.
- `src/workspace.ts` owns explicit Domain, Agent and Team creation and current-record edits.
  Agent tools merge only changed permission keys.
  Place edits apply additions/removals to current assignments, not a stale complete set.
  Archived Agents retain archive state and restore places during profile edits; assignment edits require restoring them first.
  Team name/purpose edits preserve current membership, and explicit membership edits refuse missing or archived Agents.

## Risks

- **R1** (retired 2026-11-10 with D30) Linked omp chat had real native powers outside Workbench's switches and Undo. Nothing in the app reaches omp now.
- **R2** Because the domain agent joins every crew (D6), most staffed projects become rooms (D7).

  Every onboarding steward checks in daily except those for domains you named, which check in on Mondays (D42); watch whether five or six morning check-ins on day one feel like noise.
- **R3** A team on a project adds its whole membership to the room, so large teams make noisy rooms. `@name` keeps replies targeted.
- **R4** A proactive review completes tasks and archives projects while nobody watches, now on a model's judgement (D43). The 5-change cap (D23), archiving limited to projects the browser finds quiet, and drift-refusing Undo bound it. Watch for archives and tick-offs you didn't expect.
- **R5** A shared agent's instructions are untrusted text from a stranger and go into the live prompt once added.
  The dialog shows them before Save and the function's existing limits apply; watch for prompt-injection attempts in popular shares and add moderation (report, hide) before the community grows.
- **R6** Linked folders (D47) make replies longer and dearer: a question about files is still one reply against the cap, but file text fills the context window (up to 8,000 characters a file, four per reply), so it spends more of the shared Neurons budget (launch plan R2).
  A file's text is also untrusted: a document that says "ignore your instructions" reaches the prompt like a shared agent's instructions (R5); the markers and the prompt's rule lower the odds, they don't remove them.
  Agents can still only propose, and every proposal needs Apply or has Undo, which bounds the damage; watch spend by agent (D45) and how often people link a folder before widening it.
- **R7** A memory outlives the reply that made it (D49), so a wrong one, or one an injected text talked the model into, keeps steering every later reply in that place.
  Only the person's own words can be quoted, replies that read files remember nothing, and each memory shows as a pill with Undo and in Briefing with Forget; a quote can still be a real phrase of theirs bent into a different memory.
  Watch how often memories are undone or forgotten against how many are saved (D49's counts), and whether old ones contradict newer messages, before raising the 40 an agent reads; Remember can be switched off per agent.
- **R8** Agents that ask each other (D50) can ask too often, spending your attention and, on Atlaswork's model, the shared daily replies (each answer is one).
  The prompt says to answer from their own places whenever they can, a question needs your OK unless you let that pair talk, routines always wait, and a question travels one hop.
  An answer is model text from another agent's places, so an instruction planted in a note there can reach the asker's chat; it arrives as that agent's words, never as instructions, and still can't change anything without the usual proposal and Apply.
  Watch the share of questions declined (D50's counts) before letting routines send questions on their own.
- **R9** An image is untrusted like a file (R6): a photo of a page that says "ignore your instructions" reaches the agent as described text.
  The seeing model is told never to follow instructions in the image and the agent reads the description as the person's data; proposals still need Apply or have Undo.
  Our plan pays for each description (D58); watch Neurons per reply with images before raising the four images and files a reply may open.
- **R10** People (D71) put other people's details into the workspace and the prompt: a sister's diagnosis noted in passing reaches Kin, and the model provider, though she never chose to share it.
  The person's domain bounds which agents read it, and agents don't remember health, beliefs, sexuality or politics about someone else; notes the person writes stay theirs to keep.
  The privacy notice (`landing/privacy.html`, "People you keep", 2026-11-21) says that what you keep about someone reaches the model like any note an agent reads, and asks you to keep only what they would expect.
- **R11** Agents acting on a real computer (D78) turn an instruction planted in a file, a page or an email from a bad proposal into a real action.
  The warning comes from code (D79, built first, on what a reply reads and writes), tidying waits for the person per write mode and has Undo, and a trusted helper comes later.
  Watch how often warnings show, and on what, and tidying's Undos before widening the abilities, and never add a shell.
- **R12** The desktop app's credential (D77) lets the server send work to a person's computer, so a leaked server key reaches every connected computer.
  Each computer's credential is scoped and revocable, and the service refuses any ability its computer hasn't turned on.
- **R13** The desktop app's update key (D85) can put code on every installed computer: with it and write access to the updates bucket, someone could publish their own update.
  The key and its password stay in Bitwarden and only the release reads them, the bucket takes writes from the service role alone, and the app installs only what that key signed.
